# SAMMI → Hue Scenes — Development Plan

Oct 27, 2026 · @Mike Dyer

## Overview

A SAMMI deck that turns any SAMMI trigger (a chat command, a redeem, a tip alert, a hotkey, a timer) into a Philips Hue scene, a fixed color, a white temperature, on or off, with an optional effect (breathe, candle, fire and the other Hue effects) on top, on one bulb, a room or a zone. SAMMI (already running on the streaming PC) matches the trigger and sends HTTP calls to the Hue Bridge on the LAN. No cloud piece.

1. An event the user cares about reaches SAMMI through whichever platform account is linked in SAMMI.
2. The user has attached that event as a trigger to one of the deck's action buttons (right-click > Edit Triggers). Ten example action buttons ship (scene, color, Reset, effect, scene + effect, color + effect, breathe, off, on, scene sequence). The deck ships no triggers of its own.
3. The action button holds only settings. It calls the shared **Hue: apply (shared)** button with Trigger Button. That button reads the caller's settings and runs `curl.exe` through SAMMI's **Command Line** command, sending `PUT /clip/v2/resource/scene/{id}` (recall a Hue scene) or `PUT /clip/v2/resource/{light|grouped_light}/{id}` (color, white, on, off, breathe), then the effect bulb by bulb, to the Hue Bridge over HTTPS (`-k`, see Phase 0 decision).
4. The bridge pushes the new state to the bulbs over Zigbee (internal; nothing to build).

Deliverables: a SAMMI deck (`deck/HueScenes.deck.json`, generated by `tools/build_deck.py`) that contains its own setup buttons, a one-page setup guide for a remote install, and a short maintenance note for the end user. `deck/HueScenes.commands.md` lists every command for review.

## Architecture and components

Everything runs on the streamer's PC and LAN; there is no cloud piece to host.

| Component | Where | Role | Owner |
| --- | --- | --- | --- |
| Streaming platform (any SAMMI supports) | Cloud | Emits the events SAMMI exposes as triggers | Streamer (account linked in SAMMI) |
| SAMMI Core | Streamer's PC | Trigger matching, variables, Command Line command (`curl.exe`) | Us (deck file) |
| Hue Bridge | Streamer's LAN, HTTPS :443 | CLIP v2 API; translates to Zigbee | Streamer (already installed) |
| Hue color bulb(s) | Streamer's room | Target light, room or zone | Streamer |
| Remote desktop (Windows Quick Assist) | Both PCs | One-time setup session | Us |

Data that lives only on his machine: bridge IP, app key, target and scene links, stored in `hue_scenes.ini` in the SAMMI folder (section `[hue]`, keys `ip`, `key`, `light`, `light_type`, `light_name`, `group_id`, `group_kind`, `scene_<n>`, `scene_<n>_name`, `scene_<n>_light`). SAMMI global variables are not persisted across restarts, so the INI file is the source of truth and every button reads it with INI: Load Text before acting. Nothing else is machine-specific.

## Hue API contract

Two endpoints do most of the work: the scene recall and the light / grouped_light PUT. Color, white, on, off and alerts are shapes of the same PUT body. Effects go to single bulbs only.

| Call | Method + URL | Header | Body | Used by |
| --- | --- | --- | --- | --- |
| Discover bridge | `GET https://discovery.meethue.com` | none | — | Setup: Discover, Auto rediscover |
| Mint app key | `POST https://{hueIp}/api` | none | `{"devicetype":"sammi#hue_scenes","generateclientkey":true}` | Setup: Pair (bridge button pressed first) |
| List lights | `GET https://{hueIp}/clip/v2/resource/light` | `hue-application-key: {hueKey}` | — | Setup: Pick Target; apply (room target: maps the room's devices to lights via `owner.rid`) |
| List rooms / zones | `GET .../clip/v2/resource/room`, `.../zone` (each has `metadata.name`, `services[0].rid` = its grouped_light) | same | — | Setup: Pick Target, Link Scenes |
| Read one room / zone | `GET .../clip/v2/resource/room/{id}`, `.../zone/{id}` (`children`) | same | — | apply: bulbs of a room/zone target for an effect |
| Read the target | `GET .../clip/v2/resource/{light_type}/{id}` (`alert.action_values`, `signaling.signal_values`, `effects.effect_values`, `timed_effects.effect_values`) | same | — | Try Action |
| Read one bulb | `GET .../clip/v2/resource/light/{id}` (`effects`, `on`, `color.xy`) | same | — | apply: per-bulb effect check and its current color |
| List scenes | `GET .../clip/v2/resource/scene` (`metadata.name`, `group.rid`) | same | — | Setup: Link Scenes |
| Read one scene | `GET .../clip/v2/resource/scene/{id}` (`actions[].target.rid`) | same | — | apply: bulbs of the scene for an effect |
| Recall scene | `PUT .../clip/v2/resource/scene/{id}` | same | `{"recall":{"action":"active","duration":300}}` | apply, look scene |
| Set color | `PUT .../clip/v2/resource/{light_type}/{id}` | `hue-application-key`, `Content-Type: application/json` | `{"on":{"on":true},"dimming":{"brightness":100},"color":{"xy":{"x":0.6915,"y":0.3083}},"dynamics":{"duration":300}}` | apply, look color |
| Set white temp | same PUT | same | `{"on":{"on":true},"dimming":{"brightness":60},"color_temperature":{"mirek":250},"dynamics":{"duration":300}}` | apply, look white |
| On / off | same PUT | same | `{"on":{"on":true},"dimming":{"brightness":100},"dynamics":{"duration":300}}` / `{"on":{"on":false}}` | apply, look on / off (off with a slot goes to `scene_<n>_light`) |
| Pulse | same PUT | same | `{"alert":{"action":"breathe"}}` | Setup: Test; apply, effect breathe (repeated `pulses` times, 2 s apart) |
| Effect | `PUT .../clip/v2/resource/light/{id}` per bulb | same | `{"on":{"on":true},"effects_v2":{"action":{"effect":"candle","parameters":{"speed":0.5,"color":{"xy":{…}}}}}}`; if the bridge answers with an error, `{"on":{"on":true},"effects":{"effect":"candle"}}` | apply, effect candle, fire and the others |
| Stop effect | same, per bulb | same | `{"effects":{"effect":"no_effect"}}` | apply, effect stop |
| Signal | target PUT | same | `{"signaling":{"signal":…,"duration":8000,"colors":[…]}}` (0, 1 or 2 colors) | Try Action only |
| Timed effect | target PUT | same | `{"timed_effects":{"effect":…,"duration":60000}}` | Try Action only |

Field limits from the v2 reference: `brightness` 0–100, `xy` 0–1 each, `mirek` 50–1000 (bulb-specific `mirek_schema`, usually 153–500), `duration` in ms. `mirek = 1,000,000 / Kelvin`. Send either `color` or `color_temperature` in one call, not both. Every look fades over 300 ms (`fadeMs`).

Named colors and whites (gamut C, close enough for stream use). `lookValue` takes the name, or a decimal `x,y`:

| Name | x | y |
| --- | --- | --- |
| red | 0.6915 | 0.3083 |
| orange | 0.6 | 0.38 |
| yellow | 0.46 | 0.47 |
| green | 0.17 | 0.7 |
| cyan | 0.17 | 0.34 |
| blue | 0.1532 | 0.0475 |
| purple | 0.2725 | 0.1096 |
| pink | 0.45 | 0.25 |

Whites: `warm` = mirek 370, `neutral` = 250, `cool` = 153, or a number from 153 to 500.

Each call is issued as `curl.exe -sk -m 8 …` from a Command Line command. JSON bodies are passed with `-d "{\"on\":…}"` (cmd.exe quoting). Pairing uses `devicetype` `sammi#hue_scenes`.

A field of a reply is only read after a String Position check shows it is there (`"data"`, `"actions"`, `"children"`, `"owner"`, `"xy"`, `"alert"` and so on). SAMMI crashes when a command reads a path that does not exist.

Rate guidance from Hue: ≤ 10 light commands/sec; grouped lights ≤ 1/sec. Sources: [Hue CLIP v2 reference](https://developers.meethue.com/develop/hue-api-v2/api-reference/), [Hue getting started](https://developers.meethue.com/develop/hue-api-v2/getting-started/).

## SAMMI deck design

The deck carries its own setup so the remote session is clicks, not typing. One deck, 23 buttons in six rows. Built by `tools/build_deck.py`, which runs `tools/audit_deck.py` first and writes nothing if the audit fails; `deck/HueScenes.commands.md` is the readable listing.

**Settings** (written by the setup buttons, read by every other button): `hue_scenes.ini` → `[hue]` `ip`, `key`, `light` (id of a light **or** a grouped_light), `light_type` (`light` / `grouped_light`), `light_name`, `group_id` (room/zone id, `none` for a bulb), `group_kind` (`room` / `zone` / `none`), and per scene slot 1–4 `scene_<n>`, `scene_<n>_name` and `scene_<n>_light` (the grouped_light of the scene's room or zone).

**Row 1, setup, clicked in order:**

| Button | Commands, in order | Result |
| --- | --- | --- |
| Hue 1: Discover | Command Line `curl.exe -sk -m 8 https://discovery.meethue.com` → Wait Until Variable Exists → String Position "internalipaddress" → If found: Parse, INI Save `ip`, Alert "Hue bridge at …"; else Popup telling you to use Hue Config: Set IP | Bridge IP stored, no typing |
| Hue 2: Pair | INI Load `ip` → Popup "press the bridge button, then OK" (pauses) → Command Line POST `/api` with `generateclientkey` → If response contains "success": Parse, INI Save `key` = `pair[0].success.username`, Alert "Paired"; else Popup with the bridge's error text | App key stored |
| Hue 3: Pick Target | INI Load `ip`, `key` → GET `/light`, `/room`, `/zone` → three Repeats build one numbered list (bulbs, then rooms, then zones) → list written to `hue_scenes_list.txt` and opened in Notepad (SAMMI's input popup does not scroll) → Wait For User Input for the number → arithmetic on the number decides bulb/room/zone; a number not on the list alerts and saves nothing → INI Save `light` (= light id, or the room/zone's `services[0].rid` grouped_light), `light_type`, `light_name`, `group_id`, `group_kind` | Target stored |
| Hue 4: Test | INI Load all → Command Line PUT `{"alert":{"action":"breathe"}}` to `/{light_type}/{id}` → Alert with the response | Bulb(s) pulse once |

**Row 2, config:** Hue 5: Probe (optional; native **HTTP Request** GET `https://{ip}/api/0/config` → Popup with the result; settles the TLS question on his PC, the deck does not depend on it), Hue Config: Set IP (input popup → INI Save `ip`), Hue: Show Settings (popup with IP, key, target and the four scene links), Hue Scenes: how it works (help popup).

**Row 3, tools:**

| Button | Commands, in order | Result |
| --- | --- | --- |
| Hue: Auto rediscover | SAMMI Startup trigger → waits 15 s → silent Discover | IP refreshed after a router change |
| Hue: Link Scenes | INI Load `ip`, `key` → GET `/scene`, `/room`, `/zone` → Wait For User Input for an optional name filter → for every room, then every zone: a heading and the scenes whose `group.rid` equals that room/zone id (String Position on the two ids; name filter via case-insensitive String Position; empty groups skipped; the group whose id equals the stored `group_id` is marked as the Hue 3 target) → list to `hue_scenes_list.txt` + Notepad → one Wait For User Input per slot 1–4 (-1 skips, a number not on the list alerts and skips) → INI Save `scene_<n>` = `scenes.data[i].id`, `scene_<n>_light` = the room/zone's `services[0].rid`, `scene_<n>_name` = "name in Room (room)"; alert states the room | Scene links stored |
| Hue: Try Action | INI Load all → GET the target → numbered list in Notepad: 8 named colors, 3 whites, on, off, then `alert.action_values`, `signaling.signal_values`, `effects.effect_values`, `timed_effects.effect_values` (each read only if the reply contains it) → Wait For User Input → send the pick → Alert naming the action button settings that give the same result, or saying it is Try Action only (signals, timed effects) | Shows what the target can do |
| Hue: apply (shared) | See below. Do not press it or attach triggers | Does the work for every action button |

**Rows 4–6, example action buttons** (no trigger attached; Persistent Variables on, so the shared button can read their settings):

| Button | look / lookValue | brightness | effect |
| --- | --- | --- | --- |
| Example: Hue scene | scene / 1 | 100 | none |
| Example: color (red) | color / red | 100 | none |
| Reset (optional) | white / neutral | 60 | stop |
| Example: effect (candle) | none | 100 | candle |
| Example: scene + candle | scene / 1 | 100 | candle |
| Example: orange + fire | color / orange | 100 | fire |
| Example: breathe x3 | none | 100 | breathe, pulses 3 |
| Example: turn off | off / (empty = target) | 100 | none |
| Example: turn on | on | 100 | none |
| Example: scene sequence | see below | | |
| Hue: Stop sequence | Stop Button/Group `hueSeq` (ongoing and queued), then drop queued `hueApply` runs → Alert | | |

Each action button is: a comment, the SETTINGS block, `Trigger Button hueApply` (queueable), then a switched-off `Trigger Button hueReset` after 10 s (all but Reset). Turn that last command on for a 10 s auto-reset.

**Action button settings** (Set String Variable, except `pulses`, so the exact text goes into the JSON body):

- `look`: `scene`, `color`, `white`, `on`, `off`, `none`.
- `lookValue`: scene = slot 1–4; color = red, orange, yellow, green, cyan, blue, purple, pink, or decimal `x,y`; white = warm, neutral, cool, or 153–500; off = empty for the Hue 3 target, or a slot to turn off that scene's room/zone (`scene_<n>_light`); on / none = empty.
- `brightness`: 1–100 (color, white, on).
- `effect`: none, breathe, candle, fire, prism, sparkle, opal, glisten, underwater, cosmos, sunbeam, enchant, stop.
- `pulses`: breathe count, about 2 s apart.
- `speed`: 0–1, for candle, fire and the others.

The Hue app cannot put effects or breathe pulses into a scene, so the effect is a separate setting that SAMMI applies on top of the look. Scenes stay the default for colors (route 1, chosen Oct 28, 2026): the streamer edits colors, brightness and which bulbs take part in the Hue app, and SAMMI is never touched.

**Hue: apply (shared)** (Allow Queue on): Trigger Pull Data `button_id` → if empty or itself: alert "press an action button instead" → Get Button Variable for the six settings from the caller → INI Load all → the look (scene recall, color, white, on, off, or nothing) → the effect → Overtime 1000 ms. Calls that arrive meanwhile queue, so bursts stay under Hue's 1 command/s for grouped lights and scene recalls, and each queued run uses its own caller's settings.

- breathe: sent to the target, or for a scene to the scene's room/zone (`scene_<n>_light`); waits 1 s after a look was sent, then `pulses` alerts 2 s apart.
- candle, fire and the others, and stop: per bulb. For a scene, the bulbs in the scene's `actions`; each bulb is read first and skipped if it lists no `effects` or the scene left it off, and the effect uses that bulb's current `color.xy`. For the target, the bulb itself, or every bulb of its room (devices mapped to lights via `owner.rid`) or zone (`children`), in the look's color when the look is a color. Bulbs are 150 ms apart. `effects_v2` first, plain `effects` if the bridge refuses.
- look off with an effect other than stop: the effect is skipped (it would turn the lights back on), with an alert.

Errors alert ("no scene linked for slot N", "unknown look/color/effect", "Hue rejected the look: …", "found no bulbs for the effect", "no bulb took the effect"); success is silent.

**Example: scene sequence** (button group `hueSeq`, Persistent Variables on): settings `scene1` / `scene2` (linked slots; `scene2` empty = one scene), `effect1` / `effect2`, `seconds1` / `seconds2` (1 or more), `whenDone` (`loop`, `off`, `stay`), `maxMinutes` (with loop: turn off and stop after N minutes; 0 = until stopped). It first runs Stop Button/Group `hueSeq` so starting a sequence stops any other, then repeats: set look scene + effect, Trigger Button `hueApply`, wait; Break ends the loop. For `off` (or loop reaching `maxMinutes`) it calls apply with look off and the slot, 1.2 s apart. More than two scenes: chain buttons with triggers.

**Phase 0 decision (TLS path): Command Line + `curl.exe -k`.** Evidence, no bridge needed:

- SAMMI Core is a GameMaker application. GameMaker's HTTP functions on Windows fail on untrusted certificates with `HttpSendRequest: The certificate authority is invalid or incorrect` and expose no option to skip verification (reports on the GameMaker Steam forum). The bridge presents a certificate with CN = bridge id signed by Signify's private root, which Windows does not trust, so the native HTTP Request is expected to fail.
- Plain HTTP (`http://{ip}/api/…`) is not a fallback: Hue states firmware released after Aug 1 (RED compliance) no longer serves HTTP, and Bridge Pro owners already see 301 redirects to HTTPS.
- `curl.exe` ships with Windows 10 1803+ and Windows 11, supports `-k`, and SAMMI's Command Line command captures its stdout into a variable.
- The Hue 5: Probe button runs the native HTTP Request once on his PC so the assumption is checked on real hardware during Phase 3. If it passes, the deck could be moved to HTTP Request later; nothing else changes.

Sources: [SAMMI Command Line](https://sammi.solutions/docs/commands/misc#commandline), [SAMMI HTTP Request](https://sammi.solutions/docs/commands/misc#httprequest), [GameMaker certificate error thread](https://steamcommunity.com/app/214850/discussions/0/385429254933359074/), [Hue HTTP deprecation discussion](https://hyperion-project.org/forum/index.php?thread/14428-hue-bridge-pro-https-instead-of-http-api-not-working/). Deck JSON format: see `docs/SAMMI deck JSON format notes.md`.

## Risks and open decisions

TLS was the only risk that changed how the deck is built; the rest are operational.

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| SAMMI HTTP Request rejects the bridge's certificate (CN = bridge id, no SAN) | Resolved | Was: blocks everything | Deck uses Command Line + `curl.exe -k` from the start. Residual risk: `curl.exe` missing on a very old Windows 10 (pre-1803); `where curl.exe` in a Command Prompt before the call. |
| `curl.exe` quoting of JSON bodies under cmd.exe | Resolved | PUT rejected with a JSON error | Bodies use `\"` escaping, no `&`, `|`, `%` or `^` characters; verified on hardware Oct 28, 2026 |
| Bridge IP changes after a router reboot | Medium | Lights stop reacting | Hue: Auto rediscover button runs 15 s after SAMMI starts; DHCP reservation if the router is reachable |
| Platform connection in SAMMI drops | Medium | Triggers never fire | Auto-connect on for the linked account |
| Bulb reset by a Hue app automation or motion rule | Low | Color reverts early | Optional Reset button restores a known state; or disable the conflicting automation |
| Bursts of events exceed Hue's rate limit (1 cmd/s on groups and scenes) | Low | Bridge drops requests | All action buttons go through Hue: apply (shared): Overtime 1000 ms, Allow Queue on |
| SAMMI crashes when a command reads a reply path that is missing | Found on hardware Oct 30, 2026 (SAMMI 2026.6.0): an effect on a room target crashed SAMMI with a missing-path error | SAMMI closes mid-event | Fixed in the generator: every reply field is read only after String Position shows it in the reply. Retest on hardware pending |
| Shared apply reads the wrong settings | Not yet confirmed on hardware | A button shows another button's look | Trigger Pull Data `button_id` + Get Button Variable per run; action buttons keep Persistent Variables on; audit checks the persistence |
| Pasting a new deck over an older one | Found during updates | Stale buttons stay in the deck | Delete the old deck first; run Hue 3 and Link Scenes again |
| A linked scene is deleted and recreated in the Hue app | Low | That button does nothing (old id) | Run Hue: Link Scenes again |
| Dozens of lights or scenes on the bridge | Resolved | SAMMI's input popup does not scroll, so the list was unusable | Lists are written to `hue_scenes_list.txt` and opened in Notepad; Link Scenes also filters by name (found Oct 28, 2026 on a bridge with many scenes) |
| Linked scene belongs to another room/zone | Found Oct 28, 2026 | Button fires, bridge says OK, the watched lights don't change (the other room's do) | Scene list marks the Hue 3 target group; the link alert and Show Settings name the scene's room; guide says to build the scene on the right room/zone |
| User edits/deletes a button, or presses Hue: apply (shared) | Low | Flow breaks | Maintenance note says not to; apply alerts when pressed directly; keep the deck JSON and the ini file backed up |

Open decisions (the deck ships defaults: the example buttons in the table above, Reset is neutral white with effect stop, no auto-reset, target = whatever Pick Target chose):

- [ ] Which events fire which action button (the user's choice; attached in Edit Triggers, nothing shipped)
- [ ] Does the color auto-reset after N seconds, or stay until the next event (the switched-off Trigger Button command at the end of each action button)
- [x] Single bulb or the whole room — both supported (Oct 28, 2026): Pick Target lists bulbs, rooms and zones; rooms/zones go through `grouped_light`. Colors by Hue scene chosen Oct 28, 2026 so the user edits colors in the Hue app.

## Handoff and maintenance

The user needs to know one recovery action; everything else is ours to do remotely.

| Symptom | What he does | What we do |
| --- | --- | --- |
| Lights stopped reacting | Click Hue 1: Discover, then Hue 4: Test | If still broken, remote session |
| New bridge or bridge factory-reset | Press bridge button, click Hue 2: Pair | — |
| Wants different colors | Edits the scene in the Hue app | — |
| Wants another button or trigger | Sends us what should fire it | Copy an example button in SAMMI (or add one in the generator and re-export); he attaches the trigger himself |
| SAMMI reinstalled | — | Import the backed-up deck, run Hue 1–4 and Link Scenes |
| Deck update | — | Delete the old deck, paste the new one, run Hue 3 and Link Scenes again |

Keep the deck JSON and his `hue_scenes.ini` in two places (his PC and ours). Review once after his first live session with the feature on.
