# SAMMI → Hue Scenes — Development Plan

Oct 27, 2026 · @Mike Dyer

## Overview

A SAMMI deck that turns any SAMMI trigger (a chat command, a redeem, a tip alert, a hotkey, a timer) into a Philips Hue scene, a fixed color or a white temperature on one bulb, a room or a zone. SAMMI (already running on the streaming PC) matches the trigger and sends one HTTP call to the Hue Bridge on the LAN. No cloud piece.

1. An event the user cares about reaches SAMMI through whichever platform account is linked in SAMMI.
2. The user has attached that event as a trigger to one of the deck's action buttons (right-click > Edit Triggers). Two examples ship: one recalls a Hue scene, one sets a raw color. The deck ships no triggers of its own.
3. The button runs `curl.exe` through SAMMI's **Command Line** command, sending `PUT /clip/v2/resource/scene/{id}` (recall a Hue scene, the default) or `PUT /clip/v2/resource/{light|grouped_light}/{id}` (fixed color) to the Hue Bridge over HTTPS (`-k`, see Phase 0 decision).
4. The bridge pushes the new state to the bulbs over Zigbee (internal; nothing to build).

Deliverables: a SAMMI deck (`deck/HueScenes.deck.json`, generated by `tools/build_deck.py`) that contains its own setup buttons, a one-page setup guide for a remote install, and a short maintenance note for the end user. `deck/HueScenes.commands.md` lists every command for review.

## Architecture and components

Everything runs on the streamer's PC and LAN; there is no cloud piece to host.

| Component | Where | Role | Owner |
| --- | --- | --- | --- |
| Streaming platform (any SAMMI supports) | Cloud | Emits the events SAMMI exposes as triggers | Streamer (account linked in SAMMI) |
| SAMMI Core | Streamer's PC | Trigger matching, variables, Command Line command (`curl.exe`) | Us (deck file) |
| Hue Bridge | Streamer's LAN, HTTPS :443 | CLIP v2 API; translates to Zigbee | Streamer (already installed) |
| Hue color bulb(s) | Streamer's room | Target light, room or zone | Streamer |
| Remote desktop (Windows Quick Assist) | Both PCs | One-time setup session | Us |

Data that lives only on his machine: bridge IP, app key and light id, stored in `hue_scenes.ini` in the SAMMI folder (section `[hue]`, keys `ip`, `key`, `light`). SAMMI global variables are not persisted across restarts, so the INI file is the source of truth and every button reads it with INI: Load Text before acting. Nothing else is machine-specific.

## Hue API contract

One endpoint does all the work; color and white temperature are two shapes of the same PUT body.

| Call | Method + URL | Header | Body | Used by |
| --- | --- | --- | --- | --- |
| Discover bridge | `GET https://discovery.meethue.com` | none | — | Setup: Discover |
| Mint app key | `POST https://{hueIp}/api` | none | `{"devicetype":"sammi#streamer","generateclientkey":true}` | Setup: Pair (bridge button pressed first) |
| List lights | `GET https://{hueIp}/clip/v2/resource/light` | `hue-application-key: {hueKey}` | — | Setup: Pick Target |
| List rooms / zones | `GET .../clip/v2/resource/room`, `.../zone` (each has `metadata.name`, `services[0].rid` = its grouped_light) | same | — | Setup: Pick Target |
| List scenes | `GET .../clip/v2/resource/scene` (`metadata.name`, `group.rtype` room/zone) | same | — | Setup: Link Scenes |
| Recall scene | `PUT .../clip/v2/resource/scene/{id}` | same | `{"recall":{"action":"active"}}` | Action buttons, mode 3 |
| Set a room/zone | `PUT .../clip/v2/resource/grouped_light/{id}` | same | same body as a light; limit 1 cmd/s | Action buttons, modes 1/2 when the target is a room or zone |
| Set color | `PUT https://{hueIp}/clip/v2/resource/light/{hueLightId}` | `hue-application-key`, `Content-Type: application/json` | `{"on":{"on":true},"dimming":{"brightness":80},"color":{"xy":{"x":0.69,"y":0.31}},"dynamics":{"duration":400}}` | Action buttons |
| Set white temp | same PUT | same | `{"on":{"on":true},"dimming":{"brightness":60},"color_temperature":{"mirek":370},"dynamics":{"duration":400}}` | Action buttons |
| Pulse (test) | same PUT | same | `{"alert":{"action":"breathe"}}` | Setup: Test |

Field limits from the v2 reference: `brightness` 0–100, `xy` 0–1 each, `mirek` 50–1000 (bulb-specific `mirek_schema`, usually 153–500), `duration` in ms. `mirek = 1,000,000 / Kelvin`. Send either `color` or `color_temperature` in one call, not both.

Preset xy values (gamut C, close enough for stream use):

| Color | x | y |
| --- | --- | --- |
| Red | 0.6915 | 0.3083 |
| Orange | 0.5614 | 0.4156 |
| Yellow | 0.4325 | 0.5007 |
| Green | 0.1700 | 0.7000 |
| Cyan | 0.2004 | 0.3344 |
| Blue | 0.1532 | 0.0475 |
| Purple | 0.4605 | 0.2255 |
| Magenta | 0.3824 | 0.1601 |
| Neutral white | 0.3127 | 0.3290 |

Each call is issued as `curl.exe -sk -m 8 …` from a Command Line command. JSON bodies are passed with `-d "{\"on\":…}"` (cmd.exe quoting). Pairing uses `devicetype` `sammi#hue_scenes`.

Rate guidance from Hue: ≤ 10 light commands/sec; grouped lights ≤ 1/sec. Sources: [Hue CLIP v2 reference](https://developers.meethue.com/develop/hue-api-v2/api-reference/), [Hue getting started](https://developers.meethue.com/develop/hue-api-v2/getting-started/).

## SAMMI deck design

The deck carries its own setup so the remote session is clicks, not typing. One deck, four rows of buttons. Built by `tools/build_deck.py`; `deck/HueScenes.commands.md` is the readable listing.

**Settings** (written by the setup buttons, read by every other button): `hue_scenes.ini` → `[hue]` `ip`, `key`, `light` (id of a light **or** a grouped_light), `light_type` (`light` / `grouped_light`), `light_name`, and per scene slot `scene_1` (+ `scene_1_name`); one slot ships (+ `_name`).

**Row 1, setup, clicked in order:**

| Button | Commands, in order | Result |
| --- | --- | --- |
| Hue 1: Discover | Command Line `curl.exe -s https://discovery.meethue.com` → Wait Until Variable Exists → String Position "internalipaddress" → If found: Parse, INI Save `ip`, Alert "Hue bridge at …"; else Popup telling you to use Hue Config: Set IP | Bridge IP stored, no typing |
| Hue 2: Pair | INI Load `ip` → Popup "press the bridge button, then OK" (pauses) → Command Line POST `/api` with `generateclientkey` → If response contains "success": Parse, INI Save `key` = `pair[0].success.username`, Alert "Paired"; else Popup with the bridge's error text | App key stored |
| Hue 3: Pick Target | INI Load `ip`, `key` → GET `/light`, `/room`, `/zone` → three Repeats build one numbered list (bulbs, then rooms, then zones) → list written to `hue_scenes_list.txt` and opened in Notepad (SAMMI's input popup does not scroll) → Wait For User Input for the number → arithmetic on the number decides bulb/room/zone → INI Save `light` (= light id, or the room/zone's `services[0].rid` grouped_light), `light_type`, `light_name`, `group_id` (the room/zone id, `none` for a bulb) | Target stored |
| Hue 4: Test | INI Load all → Command Line PUT `{"alert":{"action":"breathe"}}` to `/{light_type}/{id}` → Alert with the response | Bulb(s) pulse once |
| Hue: Link Scenes (row 2) | INI Load `ip`, `key` → GET `/clip/v2/resource/scene` → GET `/room`, `/zone` → Wait For User Input for an optional name filter → for every room, then every zone: a heading and the scenes whose `group.rid` equals that room/zone id (String Position on the two ids; name filter via case-insensitive String Position; empty groups skipped; the group whose id equals the stored `group_id` is marked as the Hue 3 target) → list to `hue_scenes_list.txt` + Notepad → one Wait For User Input prompt per slot in `SCENE_SLOTS` (one ships; -1 skips) → INI Save `scene_<slot>` = `scenes.data[n].id` and `_name` = "name in Room (room)" (group resolved by matching `group.rid` against rooms/zones); alert states the room | Scene links stored |
| Hue 5: Probe (optional) | Native **HTTP Request** GET `https://{ip}/api/0/config` → Popup with the result | Settles the TLS question on his PC; the deck does not depend on it |

**Row 2, config:** Hue Config: Set IP (input popup → INI Save `ip`), Hue: Show Settings (popup with IP, key, target and the four scene links), Hue: Link Scenes (above), Hue: Auto rediscover (SAMMI Startup trigger → waits 15 s → silent Discover), Hue Scenes: how it works (help popup).

**Row 3, example action buttons** (two, with no trigger attached; Allow Queue on so back-to-back events run in order):

| Button | Trigger | Commands |
| --- | --- | --- |
| Example: Hue scene | none shipped; the user attaches any SAMMI trigger | SETTINGS block (`colorMode` 3, `sceneSlot` 1, plus `brightness`, `colorX`/`colorY`, `whiteMirek`, `fadeMs` for modes 1/2) → INI Load all → If mode 1: PUT `color.xy` → If mode 2: PUT `color_temperature.mirek` → If mode 3: INI Load `scene_<slot>`, PUT `/scene/{id}` `{"recall":{"action":"active"}}` → Overtime 1000 ms → (switched Off) Trigger Button `hueReset` after 10 s |
| Example: raw color (red) | none shipped | same block with `colorMode` 1, `colorX` 0.6915, `colorY` 0.3083, `brightness` 100; shows how to set a fixed color without any Hue-app scene |
| Reset (optional) | none | same block with `colorMode` 2, `whiteMirek` 250, `brightness` 60 → INI Load all → the three Ifs. Turn the last command of each action button On to get a 10 s auto-reset. |

After the request, every action button checks the reply: empty → "no reply from the bridge" alert; contains `"description"` (Hue's error shape) → "Hue rejected the request: …" alert; mode 3 also alerts when the slot's ini key is 0. Successful requests stay silent.

Every value the Hue command changes lives in the SETTINGS block at the top of the button: `colorMode` (Set Local Variable; 3 = recall the Hue scene linked for `sceneSlot`, 1 = xy color, 2 = white temperature), and `sceneSlot`, `brightness`, `colorX`, `colorY`, `whiteMirek`, `fadeMs` as Set String Variable so the exact text is inserted into the JSON body. Mode 3 is the default (route 1, chosen Oct 28, 2026): the streamer edits colors, brightness and which bulbs take part in the Hue app, and SAMMI is never touched. Modes 1/2 remain for a fixed color on whatever target Pick Target chose.

Overtime 1000 ms keeps bursts of events under Hue's limit of 1 command/sec for grouped lights and scene recalls (lights alone allow 10/s, but the deck does not know which it is driving). 

**Phase 0 decision (TLS path): Command Line + `curl.exe -k`.** Evidence, no bridge needed:

- SAMMI Core is a GameMaker application. GameMaker's HTTP functions on Windows fail on untrusted certificates with `HttpSendRequest: The certificate authority is invalid or incorrect` and expose no option to skip verification (reports on the GameMaker Steam forum). The bridge presents a certificate with CN = bridge id signed by Signify's private root, which Windows does not trust, so the native HTTP Request is expected to fail.
- Plain HTTP (`http://{ip}/api/…`) is not a fallback: Hue states firmware released after Aug 1 (RED compliance) no longer serves HTTP, and Bridge Pro owners already see 301 redirects to HTTPS.
- `curl.exe` ships with Windows 10 1803+ and Windows 11, supports `-k`, and SAMMI's Command Line command captures its stdout into a variable.
- The Hue 5: Probe button runs the native HTTP Request once on his PC so the assumption is checked on real hardware during Phase 3. If it passes, the deck could be moved to HTTP Request later; nothing else changes.

Sources: [SAMMI Command Line](https://sammi.solutions/docs/commands/misc#commandline), [SAMMI HTTP Request](https://sammi.solutions/docs/commands/misc#httprequest), [GameMaker certificate error thread](https://steamcommunity.com/app/214850/discussions/0/385429254933359074/), [Hue HTTP deprecation discussion](https://hyperion-project.org/forum/index.php?thread/14428-hue-bridge-pro-https-instead-of-http-api-not-working/). Deck JSON format: see `docs/SAMMI deck JSON format notes.md`.

## Risks and open decisions

TLS was the only risk that changed how the deck is built; the rest are operational.

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| SAMMI HTTP Request rejects the bridge's certificate (CN = bridge id, no SAN) | Resolved | Was: blocks everything | Deck uses Command Line + `curl.exe -k` from the start. Residual risk: `curl.exe` missing on a very old Windows 10 (pre-1803); `where curl.exe` in a Command Prompt before the call. |
| `curl.exe` quoting of JSON bodies under cmd.exe | Resolved | PUT rejected with a JSON error | Bodies use `\"` escaping, no `&`, `|`, `%` or `^` characters; verified on hardware Oct 28, 2026 |
| Bridge IP changes after a router reboot | Medium | Lights stop reacting | Hue: Auto rediscover button runs 15 s after SAMMI starts; DHCP reservation if the router is reachable |
| Platform connection in SAMMI drops | Medium | Triggers never fire | Auto-connect on for the linked account |
| Bulb reset by a Hue app automation or motion rule | Low | Color reverts early | Optional Reset button restores a known state; or disable the conflicting automation |
| Bursts of events exceed Hue's rate limit (1 cmd/s on groups and scenes) | Low | Bridge drops requests | Overtime 1000 ms on each action button, Allow Queue on |
| A linked scene is deleted and recreated in the Hue app | Low | That button does nothing (old id) | Run Hue: Link Scenes again |
| Dozens of lights or scenes on the bridge | Resolved | SAMMI's input popup does not scroll, so the list was unusable | Lists are written to `hue_scenes_list.txt` and opened in Notepad; Link Scenes also filters by name (found Oct 28, 2026 on a bridge with many scenes) |
| Linked scene belongs to another room/zone | Found Oct 28, 2026 | Button fires, bridge says OK, the watched lights don't change (the other room's do) | Scene list marks the Hue 3 target group; the link alert and Show Settings name the scene's room; guide says to build the scene on the right room/zone |
| User edits/deletes a button | Low | Flow breaks | Maintenance note says not to; keep the deck JSON and the ini file backed up |

Open decisions (the deck ships defaults: one example button recalls the Hue scene linked in slot 1, one example button sets red, Reset is neutral white, no auto-reset, target = whatever Pick Target chose):

- [ ] Which events fire which action button (the user's choice; attached in Edit Triggers, nothing shipped)
- [ ] Does the color auto-reset after N seconds, or stay until the next event (the switched-off Trigger Button command at the end of each action button)
- [x] Single bulb or the whole room — both supported (Oct 28, 2026): Pick Target lists bulbs, rooms and zones; rooms/zones go through `grouped_light`. Colors by Hue scene chosen Oct 28, 2026 so the user edits colors in the Hue app.

## Handoff and maintenance

The user needs to know one recovery action; everything else is ours to do remotely.

| Symptom | What he does | What we do |
| --- | --- | --- |
| Lights stopped reacting | Click Hue 1: Discover, then Hue 4: Test | If still broken, remote session |
| New bridge or bridge factory-reset | Press bridge button, click Hue 2: Pair | — |
| Wants different colors | Edits the scene in the Hue app | — |
| Wants another button or trigger | Sends us what should fire it | Copy an example button in SAMMI (or add one in the generator and re-export); he attaches the trigger himself |
| SAMMI reinstalled | — | Import the backed-up deck, run Hue 1–4 and Link Scenes |

Keep the deck JSON and his `hue_scenes.ini` in two places (his PC and ours). Review once after his first live session with the feature on.
